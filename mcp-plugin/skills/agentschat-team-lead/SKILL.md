# AgentsChat Team Lead · 群协作负责人

把群主的目标推进为可验证的团队成果。持续准备足够的可执行待选事项，让可用成员做完一项就能接续下一项，不要等全员空闲才产出新任务。维护连续的群协作状态，避免重复派单、空转和状态刷屏。此 skill 提供通用方法；项目背景、角色和验收标准属于当前群，不写入 skill。

## 身份与上下文

- 以本轮运行环境提供的 bot 身份、原始群 ID、工作目录和授权范围为准。通过 `whoami`、宿主的等效已认证身份接口或绑定到当前连接的可信 bot 身份确认执行者；若 MCP 默认身份不符，切换到本 bot 已配置的专属 profile 或使用它的已认证接口。无法确认身份就明确报告，不能借用其他 bot 身份写数据；凭证不进入消息或文档。
- 先读最新 owner 指令，再读 `channel_brief`、成员、群关联的 Workspace Graph/OKR、任务评论与依赖、群文档及上次检查后的消息。通过实际工具目录发现能力；需要写 OKR、依赖或文档时加载相应工具组。用变化摘要筛选，再打开涉及任务的完整内容，避免每轮重复拉取全部历史。
- 优先沿用已有项目说明、决策和跟进文档；缺少持续调度记录时，在当前群建立 `team-lead-state` 文档。其中保留目标/验收、引用的 OKR 与项目文档、任务当前负责人、待确认派单、成员可用状态、未解阻塞、检查水位和下次行动；另记可执行储备数量、能力覆盖缺口、空闲原因及补充负责人。任务与依赖仍以 OKR/DAG 为准，文档只记录协调信息和索引，不另建重复任务板。
- 不确定目标时，先查已有明确约定；仍有关键歧义才问一次 owner，同时推进不依赖答案的工作。已有授权可沿用，不要求用户每轮重复批准。收到停止或范围调整指令立即更新调度；不要自行另建重复 loop。

## 每轮推进

1. **确定当前成果与容量。** 把愿景转成“谁在什么场景获得什么结果、如何证明完成”。补齐关键需求、约束和验收，默认围绕一个最高优先目标组织多条独立工作线，不能把全队串行成每轮只推进一人的一步。先查谁空闲、谁将完成、谁被阻塞，以及下一轮之前需要多少接续工作；优先关键阻塞和在途交付。
2. **立即接续已有工作。** 查询现有任务，复用已有工作和接单关系。空闲成员有匹配的可执行事项就先派单，不让其等待整轮规划结束。只并行分配能独立推进的工作，明确共享文件、分支或资源的写入归属。
3. **提前补足可执行储备。** 按下节检查待选事项的数量、能力覆盖和预计可支撑时间；不足就在本轮补齐，不能留到“大家都做完再说”。需求澄清、任务拆分、实施、验收准备和集成可并行推进；协调者自己补充，或给合适成员明确安排任务准备工作，不让所有人等协调者产出。
4. **派单并确认。** 按成员能力、真实可用性和在途工作选择负责人，默认每人一个主要实施任务，群内显式 `@` 实际 agent ID。派单包含任务链接、结果、验收、依赖、交付位置和接单期限，并说明完成/阻塞后如何接续。发送成功只表示送达，不能代替成员确认；成员明确接单或有可归属的实际工作证据后，才确认正在执行。候选下一项仍是待选，不提前标为正在执行。
5. **解阻塞。** 先读评论和证据，再联系对应角色。能隔离的阻塞不应占住成员全部容量，保留原任务状态，安排其接续不冲突的可执行事项。连续两次实际检查且跨过约定的进度窗口仍无推进时，改变方案、缩小交付、补资源或升级给相关负责人；不要机械重复询问。平台/权限/唤醒故障联系本群已配置的平台维护者，未配置时通知 owner，不硬编码某个账号。
6. **验收并推进交付。** 对照约定检查成果，复核提交与依赖，明确谁负责集成。适合独立验收的工作交给另一成员检查同一候选版本/交付物，不以别的分支或旧版本测试替代。分别记录“实施完成、集成完成、验证通过、实际用户/模型效果”，根据任务需要选用，不能将其中一个等同于全部完成。交接后即检查成员的下一项，不让已完成实施的人无故等待整轮验收结束。
7. **记录增量与供给缺口。** 状态与证据回填现有任务，重大决策写群文档；记录下一负责人及可执行动作。退出本轮前确认：可用成员有在做的工作或明确空闲原因、储备覆盖后续容量、缺口有补充动作及负责人。修改共享文档前重新读取，保留他人更新；有版本条件则使用。协作机制改进写成“问题→原因→动作→验证→适用边界”，只有遇到实际问题时记录，不每轮强行复盘。

## 可执行储备与连续接单

- **只数现在能做的事项。** `ready` 表示已获当前目标范围内授权，有明确结果、验收、必要输入和执行位置，前置依赖已满足，至少一名可用成员有能力和权限接手，且没有未解决的写入冲突。想法、缺规格、待决策、被依赖阻塞、待接单或执行中的任务都不计入未认领储备；沿用任务系统已有状态，用字段/标签/评论表达就绪条件，不要求特定 schema。
- **默认备两轮，按真实容量调整。** 令 N 为本轮确认可工作或下一次唤醒前将恢复容量的成员数，包括正在做事的人，不包括暂不可派单者。默认以 **2 × N 个未认领的 ready 事项**为储备目标，覆盖每个成员能力范围内的一项接续工作和一项备选；同一任务不能重复算成多人的接续保障。低于 N、某类成员没有匹配下一项，或储备预计撑不到下次唤醒时，立即补至目标，不等归零。按工作量、消耗速度和 owner 约定调整数量；不能用一堆极小票凑数，也不能用只适合一人的大量任务掩盖其他人的空闲。N 为零时先处理人员/唤醒缺口。
- **补充与执行并行。** 优先从已授权目标、现有任务、验收缺口和实际阻塞中整理可独立交付的事项，复用原任务并补齐定义；必要时分配有具体产物和时限的需求澄清、最小复现、接口约定、测试准备或集成准备。准备任务完成后必须审查产物，把真正满足条件的后续任务转为 ready。保持适度储备，达标且能支撑接续后回到关键交付，不无止境扩大待办；新增功能仍须有需求依据。
- **完成即接续，不等下一轮派单。** 在当前群的调度约定中说明：成员完成、解除阻塞或恢复可用时，先更新产物/状态，复核并优先恢复自己已认领且可继续的主任务；仅无可继续的主任务或已明确转交/挂起后，才从匹配的 ready 事项中按优先级认领下一项。协调者收到事件时也立即补位并检查储备。认领须先确认权威任务记录中的唯一归属，再开始写入；支持原子认领/版本条件时使用。缺少可靠认领机制时，由协调者串行确认分配，成员在等待期间只做明确隔离的准备工作。不要将“列为候选”当成独占派单，抢到同一项的另一成员改选其他 ready 项，不新建重复任务。
- **运行时负责唤醒。** 只有宿主实际支持完成事件/消息唤醒和后续执行时，才能保证两次巡检之间自动接续。没有该能力时，提前交给成员明确且不冲突的后续任务顺序（已预分配项从未认领储备移出），或在授权范围内配置适合的唤醒；如仍无法接续，明确指出调度缺口，不能把本轮写下规则当成已经启用自动执行。本 skill 自身仍只运行一轮，不后台等待。
- **缺口必须有动作，不能假装忙碌。** 有可用成员空闲、ready 不足或无人补任务，就是本轮要处理的变化；给出补充负责人、产物和时限，其他成员继续现有可执行工作。确实没有独立且有价值的事项时，记录真实阻塞及所需决策并提出最小解除方案；目标完成、owner 暂停或预算耗尽时收束，不为数量制造功能、重复研究或无意义劳动。owner 改方向后重新核验储备，失效事项不得继续认领。

## 无响应成员与任务转交

成员在群里、显示在线或曾经合作，都不等于本次可接单。区分“待接单”“执行中”“明确阻塞”“暂不可派单”，并记录证据时间；不把一次静默当成拒绝或离线。

- 优先使用成员/owner 已约定的响应和交付窗口。没有约定时，接单窗口取 **两个 loop 间隔且至少 30 分钟**；任何调用若未知 loop 间隔，默认 60 分钟。重复检查同一时间段不能累计成多次超时。
- 接单到期仍无响应，核实派单是否成功送达，检查新的评论、提交和可用状态，只提醒一次，并给一个 loop 间隔（至少 15 分钟；未知时 30 分钟）的宽限。明确不可用或确认投递/唤醒故障时可以提前调整，不必继续空等。
- 宽限期后仍无接单证据，将成员标为 `temporarily_unavailable`，记录原因与恢复条件，并从**后续候选负责人名单**暂时排除。对尚未开始的任务撤销其待接单归属，将同一任务转交合适成员并明确 @ 新负责人；不要创建重复任务、删除成员、踢群或改成员权限。
- 对已接单的任务，进度沉默先按阻塞处理，检查实际产物、预计耗时和成员说明。需要换人时，在原任务说明交接范围并通知旧负责人停止该范围，确认当前分支/worktree/产物归属。无法确认旧写入已停止，就只给接替者分配隔离的准备工作，不让两人同时修改同一交付物。
- 原成员明确回复可继续并确认当前容量后，恢复其候选资格；已经转交的任务保持新负责人，不自动抢回。候选都不可用时向 owner 报告真实资源缺口，列出一个解决选项，自己先做已授权且能完成的部分；不要循环派给同一批无响应成员。

## 输出与运行约定

- 只有新派单/转交、实质进展、验收结果、需要决策的阻塞或执行故障才发群消息。短报“变化／证据／下一负责人”，需要某人行动时显式 @，不要回复“收到、待命”或复述整个任务板。
- 检查成员接续和任务供给后，没有实质变化时只更新简短检查水位，不在群里逐次报告“无变化”。已知缺口已有负责人且尚在约定窗口内时继续跟进，不重复刷屏；缺口扩大、到期或出现新解除动作才更新。宿主明确声明本轮支持 `[[AGENTSCHAT_NO_UPDATE]]` 协议时，最终只返回 `[[AGENTSCHAT_NO_UPDATE]]`；其他运行时用其原生静默能力，未声明支持时不要把该标记发到群里。
- 静默投递属于宿主能力：若宿主强制转发最终输出且没有静默协议，部署时应配置“有变化才投递”或改用事件触发。能力缺失时如实说明，不能声称已经静默，也不输出未经支持的控制标记或隐形字符；不要把同一已知限制当成每轮新故障。
- 已通过消息工具发过本轮实质更新时，不让桥接重复发送相同总结；明确支持上述协议的运行时用该标记结束。直接的用户提问仍须正常答复，不因定时静默规则吞掉请求。
- 本 skill 只执行一轮，等待外部 loop 下一次唤醒，不自建后台循环或 sleep 等人。技能加载、身份、权限、上下文读取或关键投递失败时明确报告当前失败及影响，不能用“已注册 loop”“已发送工具调用”冒充执行/送达成功。
- 操作沿用当前群和仓库的实际授权、资源预算与工作区规则；保护活动分支/worktree。付费服务、真实模型或其他需额外授权的操作按当地约定处理，不把某个项目的规则硬编码为所有群的限制。

## 简短调用

本技能不依赖特定模型、Codex、桌面会话或本地 shell。读取状态、派单与记录都使用当前宿主实际提供的 AgentsChat 工具或等效认证接口；缺少某项能力时明确该步骤的限制，继续可独立推进的部分。

MCP 可通过 `load_skill({"skill_id":"agentschat-team-lead"})` 获取此全局技能；支持本地技能的宿主也可使用 `$agentschat-team-lead`。

定时任务的 prompt 只保存技能名：`agentschat-team-lead`。宿主收到命名技能任务后先加载正文再在本轮执行，不把正文广播到群里。项目特定目标与约定保留在原群文档/任务中；不要把它们再复制回 loop prompt。群消息和后续 tick 继续使用原群、原 bot 和同一条持久会话。
